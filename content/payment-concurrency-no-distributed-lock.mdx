## TL;DR

- 중복 결제·정산 어긋남을 **분산락 없이** DB 유니크 제약 + 낙관적 락으로 막았고, 충돌 재시도율 **3.1% → 0.4%**.
- Redis 분산락(Redlock)은 도입 비용·SPOF·락 만료 경합 때문에 접었다.
- p99 결제 처리 지연 **210ms → 180ms**, 중복 정산 건수 월 **17건 → 0건**.

## 문제 — 재현 조건 한 줄

동일 주문에 대해 PG 승인 콜백과 클라이언트 재시도 콜백이 **80ms 이내 동시 도착**하면,
정산 원장에 같은 결제가 두 번 적재되어 익일 대사에서 금액이 어긋났다.

처음엔 "가끔 나는 유령 버그"였다. 재현 조건을 저 한 줄로 좁히는 데 사흘이 걸렸고,
좁히고 나니 원인은 뻔했다 — **읽고-판단하고-쓰는 사이의 창(window)** 이 열려 있었다.

## 시도한 대안들 + 트레이드오프

### 1) DB 비관적 락 — `SELECT ... FOR UPDATE`

정합성은 확실하다. 그런데 결제 트래픽이 몰리는 구간에서 동일 키가 아닌
**주문 테이블 전체의 락 경합**으로 번졌고, 커넥션 풀이 마르면서 오히려 지연이 튀었다.

- 장점: 정합성 100%, 추론이 단순
- 단점: 경합 시 커넥션 풀 고갈 → p99 **210ms → 640ms** (부하 테스트 기준)

### 2) Redis 분산락 — Redlock

앱 계층에서 확장하기 좋다. 그러나 우리 규모에선 **Redis가 새 SPOF**가 되고,
락 만료(TTL) 튜닝·클럭 스큐·네트워크 파티션 시나리오까지 운영이 떠안아야 했다.
"돈"을 지키자고 신뢰 경계를 하나 더 늘리는 게 맞나 — 여기서 멈췄다.

- 장점: 앱단 수평 확장 용이
- 단점: SPOF 추가, 락 만료 경합, 운영 복잡도 ↑ (온콜 부담)

### 3) 낙관적 락 — 버전 컬럼 + 유니크 제약 ✅

동일 키 경합 빈도를 실측해보니 **전체 결제의 0.8%** 뿐이었다.
경합이 드물다면 "일단 쓰고, 충돌하면 재시도"가 가장 싸다.

- 장점: 경합 낮을 때 최적, 신뢰 경계 안 늘림
- 단점: 충돌 시 재시도 비용 — 단, 경합률이 낮아 무시 가능

## 고른 이유

두 개의 백스톱을 겹쳤다.

1. **멱등키 유니크 제약** — `(order_id, payment_intent_id)` 복합 유니크.
   중복 삽입은 DB가 **구조적으로** 거절한다. 앱 로직을 믿지 않는 게 핵심.
2. **원장 버전 컬럼** — 상태 전이는 `WHERE version = ?` 로만. 충돌 시 최대 3회
   지수 백오프(50ms → 100ms → 200ms) 재시도 후 실패 격리.

돈에서 낙관적 락을 신뢰할 수 있었던 건 **재시도가 안전장치가 아니라 유니크 제약이
안전장치**였기 때문이다. 재시도는 편의, 정합성 보장은 DB 제약이 맡는다.

## before / after

| 지표 | before | after |

| 충돌 재시도율 | 3.1% | 0.4% |
| p99 결제 처리 지연 | 210ms | 180ms |
| 중복 정산 건수 (월) | 17건 | 0건 |
| 추가 인프라 | — | 0 (Redis 미도입) |

## 남긴 것

경합률이 5%를 넘어가면 이 결정은 뒤집힌다 — 그때는 파티셔닝이나 큐 직렬화로
간다. 지금은 낙관적 락이 가장 게으르면서 정확한 선택이었다.
